# dialect-duckdb — DuckDB 方言插件

idb_engine 的 **DuckDB 方言实现** —— 本地嵌入式 OLAP 列式数据库。

SPI 接口定义见 [`api/README.md`](../api/README.md)，引擎如何消费方言见
[`engine/README.md`](../engine/README.md)。

## 元数据

| 属性 | 取值 |
|---|---|
| `driverName` / `displayName` | `"Duckdb"` / `"DuckDB (Embedded OLAP)"` |
| `jdbcDriverClassName` | `"org.duckdb.DuckDBDriver"` |
| `connectionType` | `EMBEDDED` |
| `requiresHost` / `requiresPort` / `supportsUser` / `supportsPassword` | 全部 `false` |
| `jdbcUrlExample` | `jdbc:duckdb:/path/to/data.duckdb`（或 `:memory:` / `.csv` / `.parquet` / `.json`） |
| `capabilities` | `VIEWS, INDEXES, FOREIGN_KEYS, MULTI_SCHEMA, ROUTINES, EXPORT, EMBEDDED_MODE` |

不支持：`USERS` / `PRIVILEGES`（嵌入式无用户权限）、`TRIGGERS`（SPI 默认 UOE）、
`DDL_TRANSACTION`（DuckDB 不支持 DDL 回滚）。

> 早期文档标「无 `ROUTINES`」是错的 —— 现在**声明** `ROUTINES`，走 `MACRO` / 标量 `FUNCTION`，
> UI 据此决定显隐。

## 实现要点

[`DuckDBDialect.kt`](./src/main/kotlin/com/langbiantianya/dialect/DuckDBDialect.kt) 的类级 KDoc
记了完整约束。几条关键的：

- **流式查询必须临时关掉 `autoCommit`**（与 PG / H2 / SQLite 同理）。
- **`database` 字段承载 URL 主体**，`:memory:` / `.duckdb` / `.csv` / `.parquet` / `.json`
  都能直接当 URL 后缀查；`.xlsx` 例外，走预转换（见下）。
- **自增主键** `GENERATED BY DEFAULT AS IDENTITY`；DuckDB 1.5.5.1 不接受 IDENTITY + 表级 PK
  组合，走 `SEQUENCE + DEFAULT nextval` 兜底。
- **FK 管理走 table-rebuild**（DuckDB 不支持 `ALTER TABLE ADD/DROP CONSTRAINT`，且忽略
  `CONSTRAINT fk_name` → 自动生成 `<table>_<cols>_fkey`）。
- **不支持 FK 的 `CASCADE` / `SET NULL` / `SET DEFAULT`** —— 一律改写为 `NO ACTION`。
- **`MODIFY COLUMN` 只支持 `RENAME COLUMN`。**
- Routines 走 `duckdb_functions()` 的 `macro_definition` 列（**不是** PG 的
  `definition` / `description`）；约束元数据在 `duckdb_constraints().constraint_column_names`（LIST 类型）。

`validateSqlFragment` 在通用集合外额外禁 `INSTALL` / `LOAD` / `EXPORT` / `COPY` / `SET` /
`RESET` / `CALL` 等 DuckDB 管理语句。

## Excel 预转换

DuckDB JDBC 不直接支持 `.xlsx`，由 [`ExcelToDuckDbCache.kt`](./src/main/kotlin/com/langbiantianya/dialect/ExcelToDuckDbCache.kt)
解决：POI 5.5.1 `SXSSFWorkbook` 流式读入 → 写临时 DuckDB 文件 → 业务层照常走
`jdbc:duckdb:<temp>`。缓存 key = 源文件 path + size + lastModified。

**两条容易被当成 bug 的「退化」是正确行为**：

- **列一律 VARCHAR，不猜类型** —— POI 读出的是字符串，猜成数字会毁掉前导零的订单号 /
  18 位身份证。代价是 `WHERE id > 15` 这类数值比较会报「VARCHAR 与 INTEGER_LITERAL
  不可比」，那是**对的**。
- **标识符一律不加引号** —— 加了 DuckDB 就大小写敏感，而应用侧拼 SQL 从不加引号
  （`WHERE col LIKE …` 的 `col` 已折小写），一改就对不上。代价是 ASCII 列名被折小写。

库名沿用**源文件名去扩展名**（库名会直接显示在应用库树上，写死 `converted` 的话用户
认不出自己的文件），表头行由「首行是否有任何一格像数字」判定。

> ⚠️ **教训**：这两处缺陷能一路存活，是因为方言自带的测试**只验 `buildJdbcUrl` 的字符串
> 拼接**（「`.xlsx` → URL 以 `.duckdb` 结尾」），从没打开过转换产物。
> **「拼出来的 URL 对不对」与「拼出来的东西用不用得了」是两件事**，后者才要断 ——
> 现由 `ExcelToDuckDbCacheTest`（6 项）与 `DuckDbFileSourceTest`（真库端到端）守住。
